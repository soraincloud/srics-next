## 新发现与修复

| 问题 | 复现及影响 | 修复 |
| --- | --- | --- |
| 截断的数据库被误当作新库初始化 | 在合成资料库上传原件、正常关闭后，将 `index.db` 截断为 0 字节。rc3 的 `Open` 成功创建空表，随后 `Collect` 将原件当作孤立对象删除。属于严重的数据保护缺口。 | 仅新建资料库的 `Create` 路径允许初始化版本 0。打开已有库时拒绝空文件、短文件、缺失版本、缺表或缺字段；启动执行 SQLite 结构与外键检查。报错并保留现场。复现用例在修复前失败、修复后通过；合法 v1 升级继续通过。 |
| 恢复密钥可能残留于系统临时目录 | 添加 restic 备用密钥时写入权限 600 的明文临时文件，靠 defer 删除。强制杀进程或断电不会执行 defer，因此可能留下额外总钥匙副本；不是证明其他普通用户已能读取。 | 新密钥通过子进程标准输入管道传递，参数仅含 `/dev/stdin`，不再生成该临时文件。子进程运行时检查传输通道、参数和临时目录；重试与真实 restic 恢复演练通过。用户主动导出的恢复文件仍需离线保存。 |
| 配置失败仍可能改变部分密码 | 用 SQLite 触发器注入登录密码写入失败：旧逻辑先更新保险库口令和闲置时间，再修改登录口令；界面收到失败时，保险库已改密。 | 三项设置使用同一个数据库事务，要么一起提交，要么保持原值。故障注入用例在修复前失败、修复后验证旧登录密码、旧保险库封装和旧闲置时间均未改变。配置 JSON 仍先单独持久化，不宣称跨文件和数据库的事务。 |

App 状态也显示资料索引损坏原因，启动时优先报告数据问题，不再误提示先设置密码。新增回归：`TestTruncatedDatabaseNeverBecomesEmptyLibrary`、`TestDamagedSchemaStopsStartupAndPreservesObjects`、`TestManagerReportsDamagedLibraryWithoutRequestingNewPassword`、`TestRecoveryPasswordNeverUsesPlaintextTemporaryFile`、`TestFailedCredentialChangePreservesBothPasswords`。破坏性故障注入只针对临时合成资料。

## 仍需明确的边界

- 软件审查与测试无法证明没有未知漏洞，不能承诺任何硬件和文件系统损坏都能恢复。索引校验也不能识别任意看起来合法的内容改写。
- 备份进程被强制结束后，`staging` 内可能保留临时快照的硬链接和索引，占用空间。本轮未引入自动递归清理，以免与仍存活的备份子进程或故障恢复现场冲突；出现异常空间占用时，应停止相关进程并核对快照用途后处理。升级前的 `before-*.db` 是保留的索引副本，不应按临时垃圾一并删除。
- 当前仍无外部备份失败通知。必须关注最后成功备份时间；停机、睡眠、断网和云凭据过期都会影响每日备份。FileVault 解锁与用户登录前，当前 LaunchAgent 不会运行。
- 尚未进行目标 Mac 实际断电、100 GB 真实负载、云账号误删防护和跨设备恢复验收。本轮没有重新进行浏览器逐页视觉验收。

**作为唯一日常资料入口前，仍需完成：真实云备份及完整读取校验、独立离线恢复文件、云账号恢复与防永久误删配置，以及另一台机器上的完整恢复。完成前保留源文件副本。** 云端服务商尚未确定，本轮没有创建或修改云资源。

第一轮的完整威胁边界、备份内容与部署验收条件继续见[安全与长期保存检查](SECURITY_2026-09-28.md)。
